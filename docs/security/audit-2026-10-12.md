# Security audit 2026-10-12: KillSwitch 0.18.1 (whole product)

- Base: 0.18.1 (25), `a5d22cb`. Addendum: the `killswitch` CLI branch (`0f1797d`, ADR 0025).
- Scope: the root side (`Helper/ks`, `install.sh`, the XPC daemon, the content filter), the
  inputs an attacker controls (subscription body and headers, Xray JSON, QR, Wi-Fi names,
  loopback ports, NetBird's plist and binary), the kill-switch guarantees, and the update chain.
- Method: code reading; logic checks with stubs as an ordinary user in a scratch directory
  (no sudo, nothing installed, pf, DNS, NetBird and the VPN untouched). Evidence levels:
  **reproduced** (a stub harness or a test run shows the behaviour), **from code**, **inferred**.
- Previous audit: `audit-2026-10.md` (0.12). Its closed points were not repeated; its open points
  are re-checked at the end.

No critical findings. No root command injection was found: every root command is an argument

### KS-09 (High): root executes NetBird's binary after its signature check fails

`netbird_sync` tags NetBird's launchd job with `_ksnetbird` only while the binary named by
`ProgramArguments:0` of `/Library/LaunchDaemons/netbird.plist` is signed by NetBird's team. When
that binary changes and the check fails (`want=0`, `have=1`), the code removes the group and then
calls `nb_connected` (line 510), which runs `nb_cli`: `perl … exec "$(nb_bin)" status …` as root.
So the binary that has just been found foreign is executed by root within about 10 s (the
watchdog's `netbird_bg` pass). `nb_reconnect` likewise runs `nb_cli … up` as root, and the
signed case has a race of several seconds between `codesign -v` and `launchctl bootstrap`/`nb_cli`.

- Attacker: a process running as a user who can write the directory of NetBird's binary. On Intel
  Macs with Homebrew, `/usr/local/bin` belongs to that user. Preconditions: NetBird installed,
  `tailscale=1` (the default), the `_ksnetbird` group present (install.sh creates it).
- Result: local privilege escalation to root without the password, immediately. NetBird's own
  daemon would also run the replaced file at its next start; KillSwitch makes it immediate and
  runs it on purpose after rejecting it.
- Reproduced: `Helper/tests/netbird.sh`-style stubs (fake `codesign`, `dscl`, `launchctl`), a
  signed-then-replaced executable at the plist's path: after `netbird_sync` the replacement ran
  with `status --daemon-addr unix:///var/run/netbird.sock`.
- Fix: never execute `nb_bin` as root. Run the CLI as an unprivileged user (or talk to the
  daemon socket directly), or drop the reconnect. At minimum: do not call `nb_connected` when
  `want=0`; before any exec require the binary and every parent directory to be root-owned and
  not group/other-writable, and run `codesign -v` immediately before, on a file descriptor or a
  root-owned copy. Treat a user-writable path as "not NetBird" (no group tag).

### KS-10 (High): Xray server switch widens egress without the admin

With Xray (ADR 0020) the subscription is an array of full configs. `check()` validates all of
them and all their servers are approved, but `build()` computes the DIRECT signature, the egress
reasons and the routing report only from the selected element (`$ci`, lines 1444-1446). The
admin's approval at import (`approved-direct`) therefore covers only that element.
`ks core select Сервер <name>` is passwordless (sudoers, `passwordless_args_ok`, the daemon) and
calls `xray_select` → `core_rebuild` → `core_commit`, which publishes the new `egress` without
`refresh_check`. If another element routes traffic to a `freedom` outbound, pf's rule becomes
`pass out quick group _ksvpn` and that traffic leaves outside the tunnel while the app shows the
VPN connected. The next refresh is then refused (signature mismatch), but the switch already
happened.

- Attacker: the subscription provider or a compromised panel (an element with direct routing
  and a harmless name); the switch itself is done by the user, a Shortcut, the CLI, or any local
  user (KS-11).
- Reproduced: the generator's own perl (`KS_XRAY_PL`, `build()`) on a two-element array with the
  same servers: element A gives `egress=[]` and an empty signature, element B gives
  `egress=[rules]` and a two-line signature.
- Fix: compute `direct`/`egress` for every element at import and approve their union (or one
  signature per element, stored and compared at `xray_select`); or make `xray_select` run
  `refresh_check` against `approved-direct` and refuse with exit 3 like a refresh.

### KS-11 (Medium): passwordless daemon commands for every local user

The daemon checks the peer's code signature, not the user. `Endpoint(uid:)` is used only for
`install` (the sudoers name) and `diagReport` (`DiagReport.mayCollect`). Every other passwordless
command (`coreOff`, `coreOn`, `coreSelect`, `coreRefresh`, `protectionOn`, `netRestore`,
`upgrade`) runs for any uid whose process is our signed app. The sudoers line grants them to one
user only, and ADR 0010 presents the daemon's set as "what sudoers allowed".

- Scenario: a second (non-admin) account on the Mac starts the app and disconnects the owner's
  VPN (everything is then blocked: denial of service), switches servers (with KS-10: a leak), or
  refreshes the profile with its own file (bounded by `refresh_check`).
- CLI branch (ADR 0025): `Contents/Helpers/killswitch` is world-executable and needs no GUI, so
  the same is reachable from ssh sessions and other users' scripts. ADR 0025's premise "the app
  already does this without a password for the same user" holds only for the same user.
- Fix: in `Endpoint`, allow the passwordless set only for uid 0, the sudoers user
  (`DiagReport.installingUser()`) and perhaps the console user; require the right otherwise.

### KS-12 (Medium): DIRECT approval labelled as new servers

`refresh_check` exits 3 both for new servers and for a changed DIRECT/DNS signature.
`RefreshOutcome` maps every exit 3 to `.newServers`, ks's reason on stderr is dropped, and the
user sees «В подписке новые серверы…» and the generic admin prompt. A provider adding
`MATCH,DIRECT` (or DNS policy outside the tunnel) gets an admin approval that the admin believes
is about servers; within five minutes of an earlier authorization there is no prompt at all.
ADR 0013 asks for an informed approval of exactly this. Fix: a separate exit code for DIRECT/DNS
changes and a dialog that shows the difference (`direct_sig` lines, egress reasons).

### KS-13 (Medium): subscription header crashes the app

`Int64(Double)` traps for `1e30`, `nan`, `inf`; `upload + download` overflows; `Int(expire…)`
traps for a huge `expire`. One form (`upload=9223372036854775807; download=1`) is saved by
`saveStatus()` and crashes every render of the home screen, offline too. pf and the core stay
fail-closed, but the user loses the interface (disconnect, settings, removing the subscription).
Fix: `Int64(exactly:)`, reject non-finite values, clamp to 0…2^53, saturating addition, clamp
`expire` before saving. (Reproduced with the parsing code copied into a script: SIGTRAP.)

### KS-14 (Low): DHCP rule as a channel outside the VPN

`pass out quick inet proto udp from any port 68 to any port 67 keep state` matches any process.
macOS lets an unprivileged process bind a port below 1024 on the wildcard address (checked: UDP
68 on `0.0.0.0` binds as uid 501; `127.0.0.1` low ports do not). Any local program can therefore
exchange UDP with any internet host on port 67 past the kill switch. Fix: add `user 0` (the DHCP
client runs as root) and/or restrict the destination to `255.255.255.255` and the DHCP server.

### KS-15 (Low, inferred): Xray `dns` outbound outside the signature

`ks-dns` (the system resolver, 127.0.0.1:53) is routed to the subscription's own `dns`
outbound (line 1516), whose `settings` are kept as written. Depending on the pinned Xray's
`nonIPQuery` handling, queries that are not A/AAAA may be forwarded by that outbound with its
own direct dialer to its `address`/`port`. pf blocks this while `egress` is empty, but with any
approved DIRECT rule the core's group may go anywhere, and these settings are not part of the
signature, so a refresh can change them. Not verified against the binary. Fix: replace the
subscription's `dns` outbound settings with ours (or force `nonIPQuery: "reject"`), or include
`dns` outbounds in the signature.

### KS-16 (Low): password fallback still runs scripts from the live bundle

Open since the 0.12 audit. The daemon path is fixed (ADR 0010 verified copy), but `runBundled`
checks `BundleSignature.isValid(Bundle.main.bundleURL)` and then has osascript run
`bash -p <bundle>/Contents/Resources/Helper/install.sh` as root from the same user-writable
bundle. A same-user process that can write the bundle can swap the script or `ks`/the cores in
between and gets root with the password the admin typed. This path is used for the first
install and whenever the daemon cannot make its copy. Fix: inside the root shell copy the bundle
to a root-only directory, `codesign --verify --deep --strict -R=…` the copy, run from the copy.

### KS-17 (Low, inferred): no anti-rollback for the daemon binary

The `ks` downgrade guard (ADR 0012) does not cover the daemon itself: SMAppService runs
`KillSwitchHelper` from whatever bundle is at the registered path, and the requirement checks
team and identifier only, Apple Development certificates included. Every old signed DMG is public
(e.g. 0.15.1 with the `mkdtemp` lifetime bug fixed in 0.15.2). A same-user process that can
replace `/Applications/KillSwitch.app` can bring an old daemon back. Fix: keep the build number
in the root-owned `/Library/KillSwitch/installed` and have the daemon refuse to serve when its
own `CFBundleVersion` is lower; require Developer ID (not Apple Development) for both sides in
release builds.

### KS-18 (Low): update feed

The feed is HTTPS and every item is EdDSA-signed, and Sparkle refuses downgrades, so the payload
is protected. But `SURequireSignedFeed` and `SUVerifyUpdateBeforeExtraction` are not set (Sparkle
2.10.0 supports both): whoever can write release assets of `KillSwitch-releases` can promote a
signed beta to everyone (drop `<sparkle:channel>`), add an informational item or notes link to a
fake page, freeze updates, and make Sparkle download and mount an arbitrary DMG before any
signature check. The beta publish (`release.sh:382-391`) downloads the stable appcast and
SHA256SUMS, merges, re-hashes and re-uploads with `--clobber` without checking the downloaded
appcast against the sums; it also copies a `sparkle-signatures` block unchanged, which would
break updates once feed signing is enabled (reproduced on the merge function). Fix: set both
keys, sign the feed after the merge, `shasum -c` before merging, `sign_update --verify` the item.

### KS-19 (Low): Tailscale relay list

`root_file_ok … relays` accepts any `ADDR_LINE`, so `0.0.0.0/0` and `::/0` pass (reproduced);
`update-tsrelays.sh` runs without `pipefail` and trusts plain `dig` answers. A bad regeneration
committed unnoticed would open everything to every process while `tailscale=1`. Fix: accept host
addresses only (no prefix) in ks and in the script; `pipefail`; resolve over DoH.

### KS-20 (Low): provider text and links

`profile-title` keeps RTL overrides and line breaks with no length limit and is shown as the
sender of announcements and in notifications, undoing the cleaning of `announce`.
`announce-url`/`support-url` accept `tg:` (log-in and add-proxy confirmations in Telegram) and
plain `http:`. Fix: clean `profile-title` like `announce` (one line, ~64 characters); allow
`https`, `mailto` and `tg://resolve` only, or show the target before opening.

### KS-21 (Low): subscription fetch hardening

The body is read whole into memory before ks's 20 MB cap, Yams expands aliases without a limit,
and redirects are followed without a delegate (the device headers go to the redirect target).
https→http is blocked by ATS for names. Fix: a task delegate refusing non-https and cross-host
redirects, a streamed ~20 MB cap, and a node/alias limit for YAML.

### KS-22 (Low): loopback ports

`127.0.0.1:47890` (the fetch proxy) and `127.0.0.1:47891` (Xray's stats API, gRPC without
authentication) are open to every local user. 47890 only ever leads into the VPN (as documented).
47891 lets any local user read and reset the counters. A local user can also bind either port
first: Xray then starts without the API (`api-off`, by design) or not at all when 47890 is taken
(fail-closed, a denial of service); root's `xray api statsquery` (line 2382) and `diag_probe`
(line 2534) then talk to that program. Only numbers are parsed, so this is integrity of the
counters and the diagnostics only. Fix (optional): a unix socket or a per-install port, and check
the listener's pid before talking to it as root.

### KS-23 (Low): trusted Wi-Fi by name

A network with the name of a trusted one stops auto-connect. No Wi-Fi name turns the kill switch
off or pauses it, so nothing leaks unless protection is already off. Fix: optionally bind trusted
networks to BSSID or security type, or say so in the UI.

### KS-24, KS-25 (Info)

- `tailscale=1` is the default, so the relay list (202 host addresses, 80/443/3478) and root's
  UDP 41641/3478 are open even on Macs without Tailscale or NetBird. Consider defaulting it from
  whether Tailscale/NetBird is installed.
- `release.sh` checks only that `Helper/mihomo` and `Helper/xray` exist (geodata is checked
  against pins); the fetch scripts re-sign in place, so the pin cannot be re-checked. Check the
  version the binary reports, or fetch into a temporary directory during the release.
  `fetch-mihomo.sh` lacks `curl -q`; the sha256 pin still fails closed. The EdDSA signature is
  only grepped for, not verified against `SUPublicEDKey`. `docs/appcast.xml` is stale.
- Accepted by design and left as is: standby next to another VPN (ADR 0018) passes everything
  while a foreign 198.18 tunnel is up and our core is down (creating such a tunnel needs root or
  a user-approved Network Extension); `direct=1` trusts uid 0 + gid 80 (off by default); the LAN
  is open with `lan=1`.

## Addendum: `killswitch` CLI branch (`0f1797d`, ADR 0025)

- Peer validation: the daemon's requirement becomes
  `anchor apple generic and (identifier "com.lesha19.KillSwitch" or identifier "com.lesha19.KillSwitch.cli") and certificate leaf[subject.OU] = "YR58655PJ7"`;
  `Runner.makeVerifiedCopy` now uses the app-only `appRequirement`, so a bundle signed as the CLI
  is never taken for the app before install.sh. Correct.
- Authorization parity: whether a command needs the right is decided by the daemon from
  `HelperCommand.needsAuthorization`, independent of the client; `protection off` and `pause`
  without a valid external form get `notAuthorized`. The CLI only obtains a right when the same
  predicate says so. Correct.
- The CLI's `AuthorizationRef` (`AppAuthorization`): created per process, interaction allowed,
  the right is `shared false`, so the CLI never reuses the app's five minutes and every run asks
  again; the external form only travels over the code-signed connection. Correct.
- The CLI sends only its listed commands (`default: return nil`), validates names through
  `HelperCommand.isValid` and the daemon checks again. No input is turned into a path or a shell
  line.
- Concerns:
  - KS-11 applies: the CLI exposes the passwordless set to every local account, including ssh
    sessions without a GUI. Fix KS-11 before shipping the CLI.
  - The daemon does not tell the identities apart: the CLI identifier gets the whole interface
    (`coreRefresh`, `upgrade`, `diagReport`, and the authorized `install`/`uninstall`/`coreImport`).
    Today the signed binary cannot be made to send them (hardened runtime, no `get-task-allow`,
    no entitlements that relax library validation), but any binary we ever sign with that
    identifier, in any version, keeps that reach. Consider checking the peer's identifier per
    connection (`SecCodeCopyGuestWithAttributes` on the audit token) and exporting a narrower
    interface to the CLI.
  - `anchor apple generic` also accepts Apple Development signatures: a debug build with
    `get-task-allow` on a developer's Mac can be attached and made to send any message. With the
    right still required for widening commands this grants only the passwordless set (KS-17 fix
    covers it).

## Verified OK

- `ks` environment hygiene (KS-01 fix) intact: `bash -p`, `ks_clean_env`, `curl -q`, sudoers
  `env_reset`/`secure_path`; `passwordless_args_ok` matches the sudoers line and the daemon.
- Root never opens a user's path: refresh reads with `sudo -u $SUDO_UID`; the daemon copies the
  profile from a file handle into a root-only directory; `diag report` writes through `tee` as
  the caller or into a root-only folder of the daemon.
- Crash reports (fixed in 0.18.0): read as the owner, `O_NOFOLLOW`, regular file, owner match,
  link count 1, size cap, names restricted. No symlink, hard-link or TOCTOU path found.
- Root-owned settings files fail closed (`root_file_ok`); a damaged off/pause flag turns
  protection back on; rules pf refuses become a lockdown.
- mihomo profile: allow-listed top-level sections, per-type proxy keys, PEM-only certificates,
  checked `dialer-proxy`, provider allow-list, DNS/sniffer allow-lists, signature of DIRECT groups,
  rules and provider downloads; `KS-DNS` and `ks-fetch` always through the profile's proxies.
- Xray: protocol allow-list, IPv4-only servers pinned, `sendThrough`/`sockopt.interface`/`mark`
  removed, `+local`/`localhost`/`fakedns` resolvers removed, our inbounds and first rules.
- Kill-switch transitions: pf is enabled before loading, reloads are atomic (`pfctl -a … -f -`),
  the anchor is restored when another program replaces the main ruleset, the watchdog takes a
  new `ks` by SIGHUP without flushing, the Xray config rollback (0.18.0) keeps pf blocking,
  the core restart keeps DNS on 127.0.0.1 for 5 s, the boot window guard turns the network off
  at shutdown. IPv6: only link-local/multicast and the tailnet pass; DNS to the LAN is blocked
  unless `dns=1`.
- Daemon: per-connection code-signing requirement on the audit token; `HelperRight` is
  `authenticate-admin-nonshared` with a 5-minute timeout and its definition is re-checked before
  every use; install/upgrade run from a verified copy; `ks` downgrade refused.
- Content filter: trusted programs by code signature (never by path), names never match
  addresses, unknown flows dropped while no tunnel is up.
- App: no URL scheme, AppleScript or Shortcut can turn protection off or change the
  subscription; `announce` is cleaned; subscription links must be https; WireGuard import ignores
  PostUp/PreUp. Update chain: HTTPS feed, valid Ed25519 key, Sparkle 2.10.0 pinned, notarization
  and `spctl` before publishing, CI with `contents: read`, no `pull_request_target`, actions
  pinned by SHA, all downloads sha256-pinned.

## Open points of the 0.12 audit

- Signature check, then root copies from the bundle: fixed on the daemon path (verified copy);
  still open on the password fallback (KS-16).
- `ks core import` through the admin prompt has no `SUDO_UID`: closed on the daemon path (the
  profile arrives as a file handle); the fallback was not re-verified.
- Old sudoers on existing installs: closed, `install.sh --upgrade` rewrites the entry.
- 256-byte limit on names and rule providers with unknown fields: functional, unchanged.
